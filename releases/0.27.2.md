# Robyx 0.27.2

UX bugfix release for the Telegram typing indicator. Closes a long-running
complaint that the "writing..." indicator vanishes for several seconds at
a time while the agent is actively working, leaving the user unsure
whether to keep waiting or whether the bot has gone silent. No persisted
state schema changes; the `v0_27_2` migration is a no-op.

## The incident

Telegram's `sendChatAction` sets the chat indicator for ~5 seconds; the
indicator is also cleared visually on the user's client the moment any
outgoing message lands in the chat. Robyx already runs a keep-alive loop
that re-emits typing every few seconds while an agent turn is in flight,
but the loop alone is not enough: every interim message the agent sends
during processing — `[STATUS …]` updates, multi-chunk response splits —
clears the indicator on the client, and the next loop tick can be up to
the full keep-alive interval away. With the previous 4-second cadence
the user could see ≥4-second gaps of "no typing" between every status
update and between every response chunk, exactly when the bot was busiest.

The user complaint, verbatim:

> sembra refreshato ogni 5 secondi ma in realtà spesso l'agente sta
> lavorando e io non vedo lo stato di writing quindi non capisco se devo
> attendere una risposta o no

## What changed

### Three surgical fixes in two files

1. **Keep-alive cadence tightened from 4s to 3s**
   (`bot/handlers.py::_process_and_send::_typing_loop`). Telegram's
   typing TTL is ~5s; 3s gives a ~2s safety margin that absorbs network
   blips and slow scheduler ticks without the indicator vanishing.

2. **Re-assert typing immediately after every interim STATUS message**
   (`bot/ai_invoke.py::_read_stream::_send_status`). After the bot sends
   a `[STATUS …]` update to the user, `send_typing` is called right away
   so the indicator is reinstated before the user's eye has time to
   register the gap. Without this, a stream of status updates produced a
   visible flicker of "typing → message → no typing → typing" with each
   "no typing" lasting up to one keep-alive interval.

3. **Re-assert typing between response chunks, but not after the last**
   (`bot/handlers.py::_process_and_send::_send_response`). When the
   final response is split across multiple platform messages (Telegram
   4096-char cap, Discord 2000, Slack 4000), `send_typing` is called
   between every consecutive pair. The last chunk deliberately gets no
   trailing typing — the bot is done, the indicator should not linger.

### What didn't change

- Public API: nothing.
- Persisted state: nothing.
- Slack / Discord adapters: `send_typing` on Slack is already a no-op
  (Slack has no equivalent to Telegram's chat-action), and Discord's
  `send_typing` is a one-shot. The same code path is exercised on every
  platform but the visible benefit is Telegram-only — that is where the
  user complaint originated.

## Tests

Two regression tests:

- `tests/test_handlers.py::TestSendResponse::test_typing_re_asserted_between_response_chunks` —
  records the order of `send_message` and `send_typing` calls during a
  three-chunk response and asserts at least one `send_typing` lands
  between every consecutive pair of chunks.

- `tests/test_ai_invoke.py::TestReadStream::test_status_send_re_asserts_typing` —
  asserts that after `_send_status` ships a `[STATUS …]` update the
  platform's `send_typing` is called exactly once with the same
  chat / thread coordinates.

Full handlers + ai_invoke suite: **245 passed**.

## Upgrade notes

- Operators on 0.27.1 upgrade to 0.27.2 via the built-in auto-updater
  or `git pull` + `systemctl restart robyx`. The migration framework
  runs `v0_27_2.upgrade` as a no-op.
- No environment-variable or config changes. The fix is on by default.
- The visible behaviour change is Telegram-only; Slack and Discord
  users will see no difference.
