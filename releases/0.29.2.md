# Robyx 0.29.2

**Universal auto-update bridge.** Release `0.29.1` accidentally declared
`min_compatible: 0.29.0`. Because Robyx selects only the newest version tag,
an installation on `0.28.3` or older saw `0.29.1` as incompatible and could
not automatically pass through `0.29.0` first.

This release removes that floor. Every earlier semantic version is accepted by
the compatibility check, so any historical Robyx installation whose updater is
running and can reach `origin` can select `v0.29.2` directly. A previous
`0.29.1` incompatibility notification does not suppress this update because
notification state is keyed by version.

## What happens during the update

The installed updater fetches the newest tag, reads this metadata, classifies
the release as safe and compatible, and applies it. After restart, Robyx runs
the legacy data migrations and the continuous version chain in order, including
the no-op `0.29.0`, `0.29.1`, and `0.29.2` steps. Current releases additionally
use the verified exact-tag transaction, snapshot, dependency lock, smoke test,
and rollback protections introduced in `0.29.0`.

## Compatibility boundary

`min_compatible: 0.0.0` intentionally imposes no version floor. Every Robyx tag
present in this repository starts at `v0.19.0` and contains the auto-updater.
Older KaelOps release notes are preserved project history from a different
repository; software without an updater cannot initiate a remote update and
must first be installed or migrated manually.

There is no data or runtime schema change. `bot/migrations/v0_29_2.py` is the
required no-op step that keeps the migration chain continuous.
