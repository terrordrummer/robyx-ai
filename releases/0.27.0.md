# Robyx 0.27.0

**Per-workspace AI backend override.** Until 0.26.0, the AI CLI used to
drive every workspace, specialist, scheduled task, and continuous step
was a single global choice (`AI_BACKEND` in `.env`). 0.27.0 lifts that
constraint: any individual workspace or specialist can now pin itself
to a different backend (`claude`, `codex`, `opencode`) at creation
time, without touching the rest of the fleet.

## What users will notice

1. **`[CREATE_WORKSPACE ...]` accepts an optional `backend="…"` attribute.**
   Place it after `scheduled_at`. When present, the workspace's
   interactive turns AND its scheduled / continuous spawns route to that
   backend; when absent, behavior is exactly as before.

   ```text
   [CREATE_WORKSPACE name="codex-app" type="interactive" frequency="none"
                     model="balanced" scheduled_at="none" backend="codex"]
   ```

2. **`[CREATE_SPECIALIST ...]` accepts the same optional `backend="…"`.**

   ```text
   [CREATE_SPECIALIST name="codex-pair" model="balanced" backend="codex"]
   ```

3. **Validation is upfront.** Unknown backends raise an inline rejection
   before any side effect — no half-created workspace with a missing CLI.
   Supported keys are reported in the error. The set is whatever
   `bot.ai_backend.list_backends()` returns
   (`claude` / `codex` / `opencode`).

4. **The orchestrator does not need to opt in.** Existing flows that
   never include `backend=` keep using the global default; the field is
   purely additive.

## Why

Real use case: a Claude-driven Robyx fleet wanting to host a single
workspace that pairs with Codex for a specific project, without
flipping the global `AI_BACKEND` env var (which would migrate every
other workspace, specialist, and scheduled task with it). Previously
the only path was to run a second Robyx instance.

## How it works

- `Agent` gains a nullable `backend` field, persisted in `data/state.json`.
- For interactive turns, `bot.ai_invoke._invoke_ai_locked` swaps the
  caller-supplied backend for the agent's pinned one (when set) before
  building the CLI command. Lookup failures fall back to the global
  default and log loudly so a missing CLI never silently kills a chat.
- For scheduled / continuous spawns, `bot.scheduler` reads the same
  preference from the queue entry (also written at workspace-create
  time) and dispatches against the chosen backend. Same fallback
  semantics.
- Backend instances are cached per-process via
  `bot.ai_backend.get_or_create_backend()` so OpenCode's managed-config
  side effect runs at most once.

## Compatibility

- State files written by 0.26.x load unchanged: missing `backend` keys
  on `Agent.from_dict` resolve to `None`, which is the global-default
  behavior. The version-chain migration `0.26.0 → 0.27.0` is therefore
  a no-op release bump.
- Queue entries created by 0.26.x are unaffected — `entry.get("backend")`
  on a pre-0.27.0 entry is `None` and `_resolve_entry_backend` returns
  the supplied default.
