# Robyx 0.28.2

**Auto-updater hotfix — stash-pop conflict now triggers rollback.**
Closes the v0.28.0 Linux crashloop incident (Roberto, 2026-05-13): the
auto-updater's `git stash pop` step left raw `<<<<<<<` / `=======` /
`>>>>>>>` markers inside `bot/bot.py` after a non-trivial WIP collision,
Python raised `SyntaxError` on the restart, and the service spun in a
crashloop with restart counter 556 (~95 min) until the operator
intervened manually.

## The incident

Roberto had a local stash containing a WIP that added a `/restart`
command to all three platform `COMMANDS` tuples in `bot/bot.py`.
Upstream v0.28.0 also modified the same lines (added `/clear` to all
three; added `/im-the-owner` to Discord). Both sides edited the same
lines → `git stash pop` produced unmerged paths. Git left the conflict
markers in the file AND preserved the stash.

The pre-0.28.2 updater detected the unmerged paths and logged an
`ERROR` (see `bot/updater.py:_safe_stash_pop` line 387-399 in v0.28.0)
— but then proceeded to restart the service anyway. Python crashed on
the SyntaxError, systemd's `Restart=on-failure` kicked in, the bot
crashed again, repeat for 95 minutes.

The post-update smoke test at `_post_update_smoke_test` ran BEFORE the
stash pop — so it couldn't catch the conflict markers introduced
afterwards by the pop.

Codex CLI code review (run on the Linux machine, 2026-05-13) identified
the root cause: stash-pop conflict was logged-but-ignored, smoke test
was ordered before stash pop instead of after.

## What changed

- **`bot/updater.py`**: new `StashPopConflict` exception class.
  `_safe_stash_pop` gains a `strict` kwarg (default False, preserving
  error-path semantics). When `strict=True` AND `git stash pop` leaves
  unmerged paths, the function raises `StashPopConflict` carrying the
  return code, unmerged-paths list, and stderr.
- **`bot/updater.py:apply_update`** step 6 (success-path stash pop):
  now calls `_safe_stash_pop(strict=True)` inside a try/except. On
  `StashPopConflict`:
  - Notifies HQ.
  - Rolls back the code to the pre-update commit.
  - Restores the `data/` snapshot.
  - Returns failure with operator-actionable guidance (resolve the
    conflict markers manually, `git add`, `git stash drop`,
    re-trigger update).
  - Does **not** re-pop the stash — git already preserved it on
    conflict, so the operator's WIP is safe at `stash@{0}`.
- **`bot/updater.py:_check_python_syntax_in_repo`**: new helper. Calls
  Python's built-in `compile()` over every `.py` file under `bot/`.
  Catches any `SyntaxError` (the smoking-gun shape from raw conflict
  markers, but also any typo a clean pop might introduce). Called by
  `apply_update` right after the stash pop, before the session
  invalidation + restart. On failure: re-stashes the popped changes,
  rolls back code + data/.

The fix is strictly to the updater. No persisted state schema change,
no protocol change, no behaviour change to running bots. The
`v0_28_2` migration is a no-op chain bump.

## Operator notes

If you've had your service stuck in a crashloop on v0.28.0/v0.28.1 due
to this bug, the immediate manual recovery (per the diagnosis on
Roberto's Linux box) is:

1. `cd robyx-ai`
2. Backup: `cp bot/bot.py bot/bot.py.bak-pre-merge`
3. Open the file, resolve the three conflict blocks (typically in the
   `COMMANDS` tuples of `_run_telegram` / `_run_slack` / `_run_discord`)
   with a union merge — keep both sides' additions.
4. `git add bot/bot.py` (resolves the unmerged state, no commit needed)
5. `systemctl --user restart robyx.service` (or your equivalent)
6. Verify with `systemctl --user status robyx.service` and check
   `bot.log` for the v0.28.x boot notification.

The stash is preserved at `stash@{0}` — drop it once you've confirmed
the resolution captured everything.

Once on v0.28.2, the bug cannot recur: a future stash-pop conflict
will trigger automatic rollback instead of restarting into a broken
file.

## Breaking changes

None. The new `StashPopConflict` exception and the `strict` kwarg are
additive. Existing callers of `_safe_stash_pop` (all error-path
callsites in `apply_update`) preserve `strict=False` semantics and
keep their best-effort behaviour.
