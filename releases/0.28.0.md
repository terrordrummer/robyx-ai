# Robyx 0.28.0

**Discord parity for collaborative workspaces + conversation archive
(`/clear`).** Closes the spec 003 FR-013 justified violation of
Constitution Principle I (Multi-Platform Parity) for Discord — external
collaborative workspaces are now first-class on Telegram **and**
Discord. Slack remains a documented limitation pending spec 008.

Ships two coordinated feature areas:

1. **Spec 007 — Discord parity.** Telegram's collaborative-workspace
   lifecycle (Flow A pre-announce, Flow B ad-hoc add, supergroup migration,
   unauthorised-adder refusal) replicated on Discord at functional parity.
2. **Spec 007.1 — `/clear` conversation archive.** New chat command that
   archives the current conversation as a markdown file and resets the
   agent's AI-CLI session, addressing long-session performance
   degradation.

## What users will notice

### Discord collaborative workspaces (spec 007)

- **Flow A pre-announce from Telegram HQ.** The orchestrator now accepts
  `[COLLAB_ANNOUNCE name="X" platform="discord" creator_id="<your Discord id>" purpose="..."]`.
  Add Robyx to your Discord guild via the OAuth invite URL and the bot
  uses the guild's audit log to confirm you were the inviter, binds the
  workspace to the first writable channel, generates an invite link, and
  notifies HQ.
- **Flow B ad-hoc add.** Adding Robyx to a Discord guild without a
  pre-announce starts the same in-channel setup conversation as Telegram.
- **`/im-the-owner <workspace-name>` — manual claim.** When the
  audit-log lookup fails (missing `View Audit Log` permission, empty
  audit log across retries, sustained Discord API errors), Robyx posts
  an advisory in the channel asking you to type the command. Validates
  creator + platform match, then binds the workspace to the channel
  where you typed it.
- **Shared-guild safety.** A Discord guild can legitimately host multiple
  collaborative workspaces — each mapped to a different channel. An
  unauthorised user trying to add Robyx to a guild where you already
  have a legitimate workspace gets the refusal message in the offending
  channel only — the bot does **not** leave the guild, preserving the
  legitimate workspace.
- **Discord mentions in role commands.** `/promote <@123456789012345678>`
  and `<@!…>` (nickname-aware) now work, alongside the existing `@123`
  and bare-numeric forms.
- **The "not yet supported on Discord" notice is gone.** Adding Robyx
  to a Discord guild now actually does something.

### `/clear` — conversation archive (spec 007.1)

- New slash command. Type `/clear` inside a workspace, collaborative-
  workspace, or specialist topic to:
  1. Archive every turn since the previous `/clear` (or since the agent
     was created) to `data/conversations/<agent>/archive-<UTC>.md` —
     a plain-markdown transcript with `### User · HH:MM` / `### Robyx ·
     HH:MM` blocks.
  2. Regenerate the agent's AI-CLI session id and reset
     `message_count` / `session_started`. The next message starts a
     fresh session on Claude / Codex / OpenCode.
- `/clear` bare in HQ is **refused** — the orchestrator stays
  session-continuous on purpose. From HQ you can use the explicit form
  `/clear <agent-name>` to target a specific agent (escape hatch for
  specialists not easily reached by topic navigation).
- Authorisation matches `/reset`: bot owner on workspace / specialist
  agents; OWNER or OPERATOR in collaborative workspaces.

### `[GET_ARCHIVE]` macro

Any non-orchestrator agent's reply can emit:

```
[GET_ARCHIVE since="2d"]                       # this agent's last two days
[GET_ARCHIVE since="6h" name="atlas"]          # named agent
[GET_ARCHIVE since="2026-05-01T00:00Z" limit="5"]
```

Robyx intercepts the macro (same lifecycle as `[GET_EVENTS]`), reads the
matching archive markdown files, and injects them into the agent's
context for the same turn. Limit `1..50`, default `10`.

## Config knobs (env vars with sane defaults)

| Var | Default | Purpose |
|---|---|---|
| `DISCORD_INVITE_TTL_DAYS` | 7 | TTL of generated invite links. `0` = no expiry (Discord sentinel). Invalid/negative values fall back to the default with a WARN log. |
| `DISCORD_INVITE_MAX_USES` | 10 | Usage cap on invite links. `0` = unlimited. |

## Required Discord bot OAuth permissions

Granted via the bot invite URL when you authorise Robyx:

| Permission | Why |
|---|---|
| `Send Messages` | Post responses in the bound channel and in HQ. |
| `Manage Channels` | Topic / thread renames for spec-006 state markers. |
| `Create Instant Invite` | Generate the invite URL Robyx attaches to the HQ notification. |
| `View Audit Log` | Resolve "who added me" on `on_guild_join`. Without it, the bot falls back to the `/im-the-owner` manual-claim path — every Flow A bind needs a manual step but otherwise works. |

## Migration v0_28_0

Normalises `data/collaborative_workspaces.json`:

- Records missing the `platform` field get `platform: "telegram"`.
- Records with `chat_id: int` get coerced to `chat_id: "<int>"`.

Pure data transform — no platform side effects, no API calls. Strictly
idempotent (re-running produces an identical file). Atomic via
temp-file + `os.replace`. A pre-spec-007 backup file round-trips through
the migration to a byte-equivalent record set modulo the new `platform`
/ `chat_id: str` fields.

`bot/collaborative.py:CollabWorkspace.__post_init__` and `from_dict`
both tolerate legacy `chat_id: int` records on load — even if the
migration is reverted, the in-process compat path keeps the loader
working.

## Breaking changes

**None for end-user workflows.** Telegram-only deployments see no
behavioural difference; the migration is a one-shot in-place normalisation.

Internally, the `Platform` ABC gains three optional callable attributes
(`on_added`, `on_removed`, `on_migrated`) and a `bot_user_id` property.
The collaborative-workspace handler signatures changed to accept
platform-agnostic `LifecycleAdded` / `LifecycleRemoved` /
`LifecycleMigrated` dataclasses; external code calling these handlers
directly (unsupported but possible) must adapt.

## Constitution alignment

This release **closes** the justified violation of Principle I declared
in `specs/003-external-group-wiring/spec.md#FR-013` for Discord. Slack
remains a documented limitation; spec 008 closes the corresponding gap
using the same lifecycle abstractions (`ChatRef`, `LifecycleAdded` /
`Removed` / `Migrated`, `Platform.on_added` / `on_removed`) introduced
here.

Principle II (Chat-First Configuration) is preserved: every new
user-facing knob (`[COLLAB_ANNOUNCE platform="discord"]`,
`/im-the-owner`, `/clear`, `[GET_ARCHIVE]`) is chat-driven; the two
invite-link env vars are operator-tunable but have sensible defaults.
